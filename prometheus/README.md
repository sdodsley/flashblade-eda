# Prometheus

The zero-code path. A FlashBlade pushes its own metrics as OTLP; Prometheus
receives them, evaluates `flashblade.rules.yml`, and Alertmanager posts the
alerts to `extensions/eda/rulebooks/alertmanager.yml`, which runs the same
playbooks as the polling rulebooks. Nothing is scraped and no exporter runs.

| File | What it is |
| --- | --- |
| `flashblade.rules.yml` | the alert rules, generated by `tools/telemetry_rules.py` from the array's own policy listing; commit the regenerated file |
| `prometheus.example.yml` | the receiver configuration (no scrape jobs; `otlp` settings, rule file, Alertmanager) |
| `alertmanager.example.yml` | the route to the rulebook's listener, grouped by `alertname` and `array_name` |

## How the array pushes

Purity//FB 4.6.4 (REST 2.21) has twelve built-in telemetry metric policies
(`GET /telemetry-metrics-policies`, 35 metrics between them: array
performance, space and connectors every minute, state, client, file
system, bucket, account and replication every ten) and pushes them to any
telemetry target attached to the policies. The FB_2_21 SDK has no
telemetry methods, so the two modules use REST:

```
- sdodsley.flashblade_eda.purefb_telemetry_target:
    name: eda-prom
    endpoint: prom.example.com:9090/api/v1/otlp/v1/metrics       # host:port[/path], no scheme
    transport: otlp-http-protobuf-without-tls         # a plain receiver; otlp-http-protobuf needs a certificate the array trusts
    source: 2200-datavip                              # a network interface of the array; the management interface is refused
    policies: "{{ telemetry_policies }}"              # the twelve names in vars/example.yml
    test: true                                        # GET /telemetry-targets/test: the array proves the path
```

`playbooks/telemetry_setup.yml` does the same from the vars keys
`telemetry_target_name`, `telemetry_endpoint`, `telemetry_source`,
`telemetry_transport` and `telemetry_policies`. Three things the array
insists on: the endpoint carries no scheme and must answer a TCP connection
when the target is created (an endpoint nothing listens on is refused), the
source is a reference to one of the array's own interfaces (a data VIP
works), and `enabled` on a policy is read-only on 2.21, so the switches
are the target's own `enabled` flag and its attachment to the policies.
`telemetry_endpoint` empty in the vars file leaves the telemetry rules
inactive.

## Running the receiver

Prometheus 3.5 or newer with `--web.enable-otlp-receiver` and
`--web.enable-lifecycle`, the configuration from `prometheus.example.yml`
(`promote_all_resource_attributes: true` is what turns the array's name
into the `device_name` label the rules read), and Alertmanager with
`alertmanager.example.yml`:

```
# /etc/systemd/system/prometheus.service
[Unit]
Description=Prometheus OTLP receiver for FlashBlade
After=network-online.target

[Service]
User=prometheus
ExecStart=/usr/local/bin/prometheus \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.path=/var/lib/prometheus \
  --web.enable-otlp-receiver \
  --web.enable-lifecycle
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

```
# /etc/systemd/system/alertmanager.service
[Unit]
Description=Alertmanager for the FlashBlade rulebook
After=network-online.target

[Service]
User=prometheus
ExecStart=/usr/local/bin/alertmanager \
  --config.file=/etc/alertmanager/alertmanager.yml \
  --storage.path=/var/lib/alertmanager
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Copy `flashblade.rules.yml` to `/etc/prometheus/`, `curl -X POST
http://localhost:9090/-/reload` after a change, and start the rulebook on
the EDA host: `./run.sh extensions/eda/rulebooks/alertmanager.yml`
(`alertmanager_host`, `alertmanager_port`, default 5002). `prometheus_url`
in the vars file (`http://host:9090`) lets `selftest.yml` and
`telemetry_check.yml` ask the receiver whether it is alive.

A rulebook host behind NAT cannot be reached by Alertmanager, but it can
reach the receiver host; a reverse tunnel from it makes `127.0.0.1:5002`
on the receiver host the listener:

```
ssh -N -R 5002:localhost:5002 <receiver host>     # autossh for a tunnel that comes back by itself
```

Alertmanager posts to `127.0.0.1:5002/alerts` as the example configures;
nothing else changes.

## The generator

```
python tools/telemetry_rules.py fb-a.example.com FB_A_TOKEN                     # live: the array's listing and its own name
python tools/telemetry_rules.py --from-file tests/fixtures/telemetry_rules.json --array-name fb-a
python tools/telemetry_rules.py --from-file tests/fixtures/telemetry_rules.json --array-name fb-a --check
```

The token is the value of the environment variable named on the command
line and is never printed. The output is deterministic (policies and arrays
sorted); `--out` defaults to `prometheus/flashblade.rules.yml`, `--check`
exits 1 when the committed file differs, `--silence-minutes` (default 10)
is the floor of the silence window, `--array-label` (default `device_name`)
is the label that names the array on every series, and `--array-name` is
the value that label carries, once per array the receiver sees (live, it
defaults to the array's own name). `tests/unit/test_telemetry_rules.py`
regenerates the file from the fixture listing and compares it with the
committed one, so a regenerate is also a test run. Regenerate when the
array's policy listing changes; 4.8.6 makes the resolution per rule and the
window follows the watched metric's own resolution.

## What the silence rule means

With push there is no `up == 0`. `FlashBladeTelemetrySilent` fires, once
per policy and array, when the policy's first metric has been absent for
twice the policy's resolution or the floor, whichever is longer: ten
minutes for the one-minute policies, twenty for the ten-minute ones.
Silence has four causes the alert cannot tell apart (a dead array, a dead
path, a disabled or detached target, a receiver fault), so the rulebook
runs `playbooks/telemetry_check.yml`, which asks the management VIP whether
the array is alive, the receiver whether it answers, and the array to run
`GET /telemetry-targets/test`, and records a verdict of `array`, `receiver`,
`pipeline` or `healthy`. One alert per policy means a single policy that
stopped (replication on an array that replicates nothing, buckets on an
array without an object store) fires alone; silence that one in
Alertmanager rather than widening the window.

`absent_over_time` carries only the labels its selector pins, so every
silence rule names its array in the selector and sets `array_name` from
that; the rulebook turns `array_name` into `target_array` through the
`telemetry_array_names` map in the vars file (device name to inventory
name; an array missing from the map is addressed by the label as it is),
because an array names itself in telemetry by its own host name and not
by its inventory name (`fb-a`). The per-client policies get
no silence rule: they push nothing while no client is active. The translated names, the `device_name` attribute and the
space and performance labels are confirmed against a Prometheus 3.16
receiver; the one `verify:` left is the health gauge's
enum (5 for every healthy component on 4.6.4, so any other value
alerts). Regenerate after a Purity upgrade and compare.
